Setup guides

How to install LM Studio
1Download LM Studio from lmstudio.ai ↗
2Open the Model Search tab, download models you like that are advised as being able to run on your hardware
3Go to the Developer tab and start your server by clicking the slider button
4Recommended: in the Developer tab, enable API Authentication and copy the generated API key — paste it into the API key field above when adding this server. Without a key, any process on your machine can send requests to LM Studio.
How to install Ollama
brew install ollama

Or download the macOS app ↗

curl -fsSL https://ollama.com/install.sh | sh
Download Ollama for Windows ↗
ollama serve
Running on a VPC, cloud VM, or remote server

You only need to install the inference software on the remote machine — not Logos.

Ollama on a Linux VM

curl -fsSL https://ollama.com/install.sh | sh

Then expose the API publicly (binds to all interfaces):

OLLAMA_HOST=0.0.0.0 ollama serve

Then pull your model: ollama pull qwen2.5:14b

vLLM on a GPU VM

pip install vllm
vllm serve Qwen/Qwen2.5-14B-Instruct --host 0.0.0.0 --port 8000

Networking checklist

  • Open the inference port in the VM's firewall / security group (e.g. TCP 11434 for Ollama, 8000 for vLLM)
  • If behind a private VPC with no public IP, use a VPN, SSH tunnel, or reverse proxy
  • On AWS/GCP/Azure: add an inbound rule in the security group / firewall for the port

Quick SSH tunnel (no firewall changes needed)

ssh -L 11434:localhost:11434 user@your-vm-ip

Then add http://localhost:11434 as your server URL above — traffic tunnels securely.

What do these scores mean?
tok/s — tokens per second: how fast the model generates text. Higher is better. Agent conversations feel sluggish below ~6 tok/s. ≥30 fast 15–29 good 6–14 usable <6 slow
ttft — time to first token: how long from request sent until the model emits its first byte. This is network + model loading + prompt processing. Separate from tok/s which measures streaming after the first byte. ≤500ms snappy 500ms–2s ok 2–4s sluggish >4s bad
Hi! Xms — full round-trip latency on a "Hi!" prompt (from POST to first visible reply token). This is the closest number to "what a user feels" when they type and wait. Includes ttft plus any reasoning-mode thinking before the first visible reply. Reasoning models (qwen3, etc.) will show a higher number here than their ttft because they think before speaking.
ctx — context window: the maximum number of tokens the model can hold at once (your message + its reply + everything in between). The agent system prompt + tools uses ~17K tokens. LM Studio splits context across 4 parallel slots by default, so a 32K model only provides 8K per request. Models under 64K ctx are not eligible (16K/slot minimum) — they show a ⚠ and cannot be selected. Models with ≥128K context support 4 concurrent users at 32K/slot. For smaller models, reduce "Max Concurrent Predictions" in LM Studio advanced settings to increase per-slot context.
N/6 (with ✓ or ⚠) — base capability eval. Six standardised tests: instruction following, reasoning, structured output (JSON), tool selection, nested JSON, and multi-step arithmetic. Models that fail format or tool-call tests are de-prioritised because they break agent loops mid-conversation. Click any tested model to see the per-test breakdown.
★N (gold star) — hard eval: extra harder cases that separate "okay" models from genuinely strong ones (longer reasoning chains, trickier formatting, edge-case prompts). Higher is better. Only present when the model has been benchmarked against the hard suite.
★★N (purple double-star) — agent eval, scored out of 3: multi-turn tool loops that simulate real agent sessions (chained tool calls, recovering from a wrong call, holding a plan across turns). The clearest signal of "will this model actually work as an agent" — pay close attention to this one.
tools vision — capability badges. tools means the model accepts function-calling requests in OpenAI format; vision means it accepts image inputs. Driven by the model card, not the benchmark.
Results depend on current server load. For accurate scores, avoid running other workloads on your inference machines during the benchmark.
Scores reflect conditions at test time. A server handling other requests or services during testing may show lower throughput than usual.
